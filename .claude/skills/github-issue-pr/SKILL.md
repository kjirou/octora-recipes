# GitHub issue / PR 操作ルール

`gh issue` / `gh pr` で issue や PR を作成・編集・レビューする時は、以下に従うこと。

## 本文を編集する前に必ず fetch する

issue / PR / **コメント**の本文を編集する時は、**直前の状態をローカルに保存していても、会話の冒頭で取得済みでも、必ず取得し直してから更新する**。

- issue / PR 本文: `gh issue view <num> --json body --jq .body > <scratchpad path>` で取得し直してから編集する
- issue / PR コメント: `gh api repos/<owner>/<repo>/issues/comments/<id> --jq .body > <scratchpad path>` で取得し直してから編集する
- 取得した本文に対して、必要な差分のみ加える
- ローカルにキャッシュした古い本文を再利用しない

ローカルコピーはユーザーや他セッションの編集で陳腐化している可能性があり、古い本文で edit 系 API を叩くと他の編集を上書きで消してしまう。特に手動テストのチェックリストコメントはユーザーがチェックボックスを進める形で頻繁に更新されるため、fetch を挟まないとチェック状態を巻き戻す事故になる。

## タイトル

**issue / PR のタイトルには他の issue / PR の番号を含めない**。PR タイトルだけでなく **issue タイトルにも**適用する。`#NNNN` 参照は prefix だけでなく **タイトル本文中のどの位置でも**含めない。

タイトルは「何をするか / 何が起きているか」を日本語で簡潔に表現する文字列のみにする。

- `gh issue create --title` / `gh pr create --title` を組み立てる時、タイトル文字列を `grep -E '#[0-9]+'` でチェックし、ヒットしたら表現を書き換える
- 「#NNNN 着手前の」「#NNNN 配下の」「#NNNN の後続」のような表現も、本文の「関連」セクションで「本 issue は #NNNN の後続」と書けばよい。タイトル側からは番号を抜く
- コミットメッセージから流用する場合も、タイトル化する時点で番号を削る
- 既存の違反タイトルを発見した場合は、状況に応じて `gh issue edit --title` / `gh pr edit --title` で訂正する

タイトルに番号を入れると、リンク先 issue が rename / close / merge された時に意味が陳腐化する。関連 issue へのリンクは description の「関連」「Closes <URL>」に置けば十分。

違反例:

- `Issue #2269: 既存の〇〇を削除する`（PR の prefix 違反）
- `#2404 着手前の〇〇の残存リスク監査`（issue タイトル本文中の参照）

## PR の description

Issue を起点として PR を提出する場合、description は `- Closes <IssueのURL>` **だけ**にする。他の情報を足さない。

### 1つの Issue を複数 PR に分割する場合

`- Closes <Issue URL>` を書いてよいのは **最後の Part だけ**。Part 1〜N-1 には書かない。

- `Closes` を含む PR がマージされると GitHub が Issue を自動クローズする。Part 1 の時点では要件を満たしていないのでクローズしてはいけない
- Part 1〜N-1 では参照のみにする（例: `- Refs https://github.com/.../issues/<N>`、または本文内で「Issue #X の Part Y/N」と明記）
- 「description は Closes だけ」は単一 PR の場合の話であり、分割 PR には適用しない
- Part 1 を作る前に、PR が何個に分かれるか・どの Part が最終かをユーザーと合意しておく

## umbrella issue の書き方

### 子Issues/PRs セクション

配下のサブ issue / PR は **`# 子Issues/PRs`** セクションで列挙する。`関連Issues/PRs` という名前は使わない。

- 列挙するのは**直接の子だけ**。親 umbrella（祖父）はこのセクションに入れない。文脈として触れたい場合は背景や目的のセクションで書く
- 子 issue 側の本文で親 umbrella や兄弟 issue を `# 関連` のような別セクションに載せるのは自由（こちらの命名は厳密でなくてよい）

「子」と「関連」を区別することで、その umbrella の責任範囲が一目で分かるようにする方針。

### TODO エントリ

TODO は `- [ ] #NNNN` の**番号のみ**で書く。タイトルは GitHub が自動表示するので説明文の併記は不要。発見経緯・確認済み事項・タイミング注記などの文脈情報も付けない。

- **番号のみでないと GitHub の tracked-issue 機能（issue クローズで自動チェック・タイトル自動表示）が働かない**。後置テキストがあると単なる手動チェックボックスになる
- 順序・依存関係など issue 本文に無い情報がどうしても必要な場合は、項目に付けずリスト前の説明文へ書く
- 発見経緯や履歴は派生 issue セクションや issue 本文・監査コメントに置く
- 未起票の TODO 項目は文脈を umbrella に書くしかないので例外。起票したら番号のみの項目へ置き換える

### 現在時点に依存する表現を書かない

umbrella issue 等の長期管理ドキュメントには、「← イマココ」「（未起票）」のような、現在時点の文脈でしか意味を持たないマーカーを書かない。

- 進捗状態はチェックボックス（`- [ ] #NNNN`）で表現し、それを唯一の状態表現にする
- 見出しは、状態が変わっても書き換え不要な安定した名前だけにする
- 「起票待ち」等の状態は「〜の完了後に起票する」というトリガー条件の記述（恒久的に正しい文）で表す

## PR レビュー

### 投稿先とタイミング

- レビュー内容は紐付いている issue ではなく **PR 側にコメントする**。`gh pr comment <num>` を使う（`gh issue comment <num>` ではない）
- レビューを依頼されたら、会話で報告するだけでなく**そのまま PR へ投稿するところまで行う**。投稿の可否を毎回質問しない
- 差分を読むのは `git show` / `git diff` / `gh pr diff` で行う。**既存の worktree で `git checkout <pr-branch>` をしない**（検証用環境を勝手に立てたのと同じことになる）。ビルドやテストによる検証が必要なら自分で worktree を切る
- ユーザーが「issue にコメントして」と言った場合でも、レビュー内容なら PR 側へ投稿する旨を伝えてから動く
- PR と無関係な仕様検討など、単発の議論コメントは issue 側で OK

### 「後続で対応」はその場でキューに載せる

「後でやる / 仕上げスライスで拾う / non-blocking」と分類した項目は、**その場で対応先 issue の本文（スコープや削除リスト）へ追記する**。分類しただけでは管理されていない。

1. 対応先 issue を特定する
2. その issue のスコープが本当にこの項目を含むか、**本文を読んで確認する**（「監査で拾えるはず」と仮定しない）
3. 含まないならその場で本文へ追記する。受け皿が無ければ起票するか、ユーザーに確認する

PR コメントには「#NNNN のスコープへ追記済み」と書けるのが完了状態。マージ後の PR コメントは誰も読み返さないので、記録先として当てにしない。
